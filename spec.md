# EVAC-TWIN — Evacuation Management Application Functional & Technical Specification

## 1. Overview & Objectives

The **EVAC-TWIN Evacuation Management Application** is an interactive decision-support and digital twin tool designed to help emergency management personnel coordinate urban evacuations, compute optimal routing paths around hazards, and run crowd and vehicle movement twins over time.

### Primary Goal (Scoping Phase)
Build a responsive, high-usability web User Interface (UI) backed by OpenStreetMap (OSM) data to allow rapid concept iteration with stakeholders. The system combines interactive GIS zone management, obstacle-aware route computation with designated assembly/pickup points, mid-twin dynamic scenario editing, and an animated agent/density digital twin with real-time heatmap visualization.

---

## 2. Target Audience & Core Workflows

- **Target Audience**: Emergency management personnel, urban planners, and civil defense coordinators.
- **Core Workflow**:
  1. Load a preset city scenario from `data/scenarios/*.pkl` or define a custom scenario from scratch.
  2. Draw or edit **Source Areas** (evacuation zones), **Target Areas** (safe shelters/assembly points), **Avoid Areas** (hazards/blocked zones), and **Vehicle Fleets** (staging depots).
  3. Trigger **Compute Evacuation Routes** to calculate optimal paths from sources to targets while avoiding Avoid Areas, respecting shelter capacities, and establishing specific **Pickup Locations (marked with blue squares)** on each Source Area for every route. While route computation is in progress, the map is disabled, a centered waiting indicator overlay with the label **`computing routes`** and a **`stop calculation`** button is displayed over the map, and when the calculation finishes or the user clicks **`stop calculation`**, the map is restored, calculated routes are included only if the calculation was not stopped by the user, and the **`stop calculation`** button is removed.
  4. Trigger **Run Twin** to animate:
      - Evacuees moving *within* each Source Area toward established Pickup Locations (including underground Brussels Metro stations when enabled) according to their behavioral profile (`compliant`, `self-directed`, `disoriented` via 2D Brownian motion with pickup-seeking drift).
      - Street vehicles traveling along computed OpenStreetMap road routes at each fleet's configured **transit speed (`transitSpeedKmh`, default `25 km/h`)** using exact Haversine geodesic distances along the underlying map polylines, arriving at Pickup Locations, progressively boarding waiting evacuees according to each vehicle's configured **average time in seconds to load/unload one person (`loadUnloadTimePerPersonSeconds`)**, and departing for Target Shelters when **either 80% occupancy is reached OR 10 minutes of waiting time have elapsed** (whichever happens first, provided there is **at least 1 passenger** onboard).
      - When **Brussels Metro Evacuation** (`Use these stations for evacuation`) is enabled, underground metro trains operate concurrently along the static STIB metro rail trajectories (`data/brussels_metro_lines.parquet` and `data/brussels_metro_stations.parquet`) between metro stations inside Source Areas and metro stations inside active Target Areas, completely independent of `Compute Evacuation Routes` and unaffected by surface `Avoid Areas`.
      - Upon reaching a Target Shelter (or Target Metro Station), vehicles and metro trains transition into an **unloading** state (`status: 'unloading'`) and progressively offload passengers into the shelter according to `loadUnloadTimePerPersonSeconds` before departing empty along the reversed route polyline (`Target Shelter -> Pickup Location`) to pick up more people.
   5. **Pause & Dynamic Mid-Twin Editing**:
      - Operators may pause (`Pause twin`) at any point to modify areas and vehicles (including changing population counts in Source Areas, disabling or enabling Source Areas, Target Areas, or Avoid Areas, adding/removing Source/Target/Avoid Areas, adding/modifying/removing vehicles, their `transitSpeedKmh`, and their per-person load/unload times, or toggling Brussels Metro evacuation parameters) under strict operational safety constraints.
      - Upon restarting (`Run twin`), routes are dynamically recomputed for all remaining and new evacuees in enabled Source Areas into enabled Target Areas (avoiding enabled Avoid Areas), and any running vehicles currently carrying passengers are immediately routed to the **closest enabled Target Area** before transitioning to the newly recomputed routes.

## 3. Domain Entities & Data Models

### 3.1 Evacuation Source Areas & Internal Population Behavior
Geographic zones requiring evacuation. The population within a Source Area **remains inside that Source Area until picked up by an evacuation vehicle**. Their behavioral profile governs how they move *within* the Source Area to reach a Pickup Location (Blue Square):
- **Name**: String identifier (e.g., `"Grand Place"`).
- **Geometry**: Polygon (`GeoJSON Polygon`) drawn on the map.
- **Total Population**: Integer count of evacuees (`N >= 0`). Can be modified while the twin is paused.
- **Disabled State (`disabled: boolean`) & Remove with Confirmation**:
  - Source Areas can be **disabled** (or re-enabled) while the twin is paused via the **`Disable` / `Enable`** button (`#btn-disable-source-{id}`). A disabled Source Area is excluded from route computation (`Basic OSM`, `evaccast_v1`, and Brussels Metro corridors) and twin evacuation simulation (no crowd dots, pickup queues, or vehicle dispatches are active for it), and is rendered in muted slate gray with a `[DISABLED]` badge on the map and parameter card. If disabled mid-twin while paused, any vehicles already carrying passengers (`currentOccupancy > 0`) from that Source Area complete delivery to the closest active Target Shelter and then reassign to an active corridor.
  - Every Source Area also includes a **`Remove`** button (enabled while paused) alongside **`Disable` / `Enable`**. Clicking **`Remove`** opens a confirmation popup modal (`#confirm-remove-area-modal`); upon confirmation, the Source Area is removed from the configuration, map, routes, clusters, pickup locations, and vehicles.
- **Constant 50 People per Dot (`PEOPLE_PER_DOT = 50`) & Spatially Uniform Initial Distribution (`sampleUniformPointsInsidePolygon` & `buildClustersForSources`)**:
  - Each dot (`SourceInternalCluster`) represents a constant **50 people (`PEOPLE_PER_DOT = 50`)** across all Source Areas, so Source Areas with fewer total people have proportionally fewer dots and areas with more people have proportionally more dots.
  - For each behavioral group (`compliant`, `self-directed`, `disoriented`) in a Source Area (`computeSourceBehaviorHeadcounts`), the twin creates $\lfloor P_b / 50 \rfloor$ full dots of `50` people plus at most `1` remainder dot with $P_b \bmod 50 < 50$ people (when $P_b \bmod 50 > 0$) so the sum of dot headcounts matches the exact total population and behavioral split in each Source Area.
  - Upon the initial setting of any scenario (on application startup, when selecting any preset scenario, when resetting the twin, or when adding/editing Source Areas at `t = 0`), all dots for each Source Area are distributed **spatially uniformly** across the interior of that Source Area polygon via a **2D Roberts $R_2$ low-discrepancy quasi-random sequence** ($\phi_2 \approx 1.324717957244746$, $\alpha_1 = 1/\phi_2$, $\alpha_2 = 1/\phi_2^2$) over the polygon interior (`isPointInPolygonRing`), refined by **3 iterations of discrete Centroidal Voronoi Tessellation (Lloyd's relaxation)** in isotropic metric coordinates ($\Delta x = \Delta \text{lng} \cdot \cos(\text{meanLat})$, $\Delta y = \Delta \text{lat}$) with concave-boundary medoid snapping and uniform behavioral interleaving.
- **Strict Source Area Polygon Containment & Anti-Corner-Trapping Deflection (`ensurePointInsideSourcePolygon`)**:
  - **All populations (`compliant`, `self-directed`, and `disoriented`) must always stay within their initial designated Source Areas** at every twin tick.
  - Every candidate movement step is verified against the Source Area's GeoJSON polygon (`turf.booleanPointInPolygon`), and any step that would cross the boundary is deflected using a full-$360^\circ$ multi-scale randomized angular fan, inward reflection toward the interior target, and a 16-direction radial interior escape probe so dots never get trapped in concave corners or sharp polygon vertices.
- **Population Walking Speed (`5 km/h`) & Behavioral Profile Distribution** (percentages summing to 100%):
  - All population groups move inside their Source Area toward Pickup Locations at a walking speed of **`5 km/h`** ($\approx 1.3889\text{ m/s}$, `kmhToMps(5)`):
  - **Compliant (`%`)**: Immediately head directly to the **closest Pickup Location** within the Source Area at `5 km/h` starting at `t = 0`.
  - **Self-Directed (`%`)**: Move towards the **closest Pickup Location** at `5 km/h` in a **random zig-zag pattern** (alternating left/right diagonal tacks of $\pm 22^\circ\text{..}50^\circ$ relative to the pickup bearing over `3.2s–7.7s` legs with per-step angular jitter), **sometimes walking in the opposite direction for very short periods of time** (`1.2s–2.4s` brief reversal legs away from the pickup point), while always staying inside their initial designated Source Area. When a boundary/corner deflection (`bounced`) occurs, the dot aligns its next zig-zag tack with the actual interior escape bearing plus randomized angular jitter (`±20°`) so it smoothly escapes corners without ping-ponging.
  - **Disoriented (`%`)**: Diffuse inside the Source Area polygon at `5 km/h` following a **2D Brownian motion (Wiener process)** combined with a stochastic pickup-seeking radial drift toward Pickup Locations inside the Source Area until they come within **135 meters** (`160 meters` for Metro stations) of any Pickup Location, at which point they direct themselves straight to it at `5 km/h`.
- **Route Pickup Locations (Blue Squares) & Partial Dot Boarding (`waiting_at_pickup` $\rightarrow$ `< 50` $\rightarrow$ `boarded`)**:
  - Specific `[lat, lng]` assembly points established strictly within the Source Area polygon once routes are computed.
  - When a dot reaches a Pickup Location, it transitions to `status: 'waiting_at_pickup'` at a deterministic waiting position around the pickup point (`computeWaitingDotPosition`, strictly inside the Source Area polygon). As part of the people represented by a waiting dot get into evacuation vehicles (depending on vehicle capacity and loading rate via `deductBoardedFromWaitingClusters`), that dot's `headcount` is reduced accordingly: the remaining part (`0 < headcount < 50`) stays visible and waiting at the Pickup Location for subsequent evacuation vehicles until all 50 people in that dot have boarded (`headcount === 0`, `status: 'boarded'`).

### 3.2 Evacuation Target Areas (Safe Zones)
Designated safe destinations or shelters where evacuees are transported by vehicles.
- **Name**: String identifier (e.g., `"Parc du Cinquantenaire"`).
- **Geometry**: Polygon (`GeoJSON Polygon`) drawn on the map.
- **Capacity**: Maximum number of evacuees the area can accommodate (`Integer`).
- **Current Occupancy**: Tracked dynamically as vehicles offload passengers (`0` to `Capacity`).
- **Disabled State (`disabled: boolean`) & Remove with Confirmation**:
  - Target Areas can be **disabled** (or re-enabled) while the twin is paused via the **`Disable` / `Enable`** button (`#btn-disable-target-{id}`). A disabled Target Area receives **no more people** (excluded from routing and mid-transit vehicle redirection), while retaining its existing `currentOccupancy`.
  - Every Target Area also includes a **`Remove`** button (enabled while paused) alongside **`Disable` / `Enable`**. Clicking **`Remove`** opens a confirmation popup modal (`#confirm-remove-area-modal`); upon confirmation, the Target Area is removed from the configuration, map, routes, pickup states, and twin memory.

### 3.3 Avoid Areas (Hazard / Blocked Zones)
Restricted or hazardous areas impassable for evacuation routing.
- **Name**: String identifier (e.g., `"Pont d'Iéna"`).
- **Geometry**: Polygon (`GeoJSON Polygon`) drawn on the map.
- **Disabled State (`disabled: boolean`), CRUD Rules & Remove with Confirmation**:
  - Avoid Areas can be **disabled** (or re-enabled) while the twin is paused via the **`Disable` / `Enable`** button (`#btn-disable-avoid-{id}`). When an Avoid Area is disabled (`disabled: true`), its hazard exclusion is suspended so evacuation routes (`Basic OSM` and `evaccast_v1`) may pass through it, and it is rendered on the map in muted slate gray with a `[DISABLED]` badge.
  - Avoid Areas can also be freely added, modified, or removed while the twin is paused. Clicking **`Remove`** on an Avoid Area opens a confirmation popup modal (`#confirm-remove-area-modal`); upon confirmation, the Avoid Area is removed from the configuration and map.
- **Strict Non-Intersection Guarantee for Active Avoid Areas (Zero Crossings)**:
  - **Evacuation routes, vehicle approach routes, and mid-twin vehicle redirection routes must never cross or touch any active (non-disabled) Avoid Area polygon** (`turf.booleanIntersects(routeSegment, avoidPolygon) === false` across every polyline segment).
  - The routing engine enforces this invariant using a **2D Obstacle Visibility Graph + Dijkstra Shortest-Path Solver** over multi-tier buffered exterior vertices around all active Avoid Area polygons:
    1. Collision-free detour waypoints are computed around all active Avoid Area polygons and passed to OSRM for road-network routing.
    2. Whenever any segment or sub-path returned by OSRM enters or crosses an active Avoid Area polygon, surgical segment-level repair replaces that sub-path with the shortest collision-free exterior visibility-graph detour around the obstacle.

### 3.4 Evacuation Vehicle Fleets, Transit Speed (`km/h`), Per-Person Loading/Unloading Time, Empty Return Routing & Dual Departure Condition
Available public or private transport units managed by authorities, modeled as **Fleets / Staging Depots**:
- **Name**: String identifier (e.g., `"STIB Bus Fleet Alpha"`).
- **Vehicle Type**: Category (`Bus`, `Private Car`, `Shuttle`, etc.).
- **Initial Location**: Point (`GeoJSON Point` — `[lat, lng]`) representing the depot or staging area at `t = 0`.
- **Unit Count**: Number of vehicles in this fleet (`Integer`).
- **Capacity per Unit**: Passenger occupancy per vehicle (e.g., `50` for buses, `4` for cars).
- **Transit Speed (`transitSpeedKmh`)**: Configured physical transit speed of vehicles in kilometers per hour (`km/h`), defaulting to **`25 km/h`** ($\approx 6.944\text{ m/s}$). Configurable when creating or editing a Vehicle Fleet.
- **Average Load / Unload Time per Person (`loadUnloadTimePerPersonSeconds`)**: Average time in seconds required to load (board) or unload (disembark) one person into or out of each vehicle (e.g., `2` seconds/person for buses, `3` seconds/person for private cars). Configurable when creating or editing a Vehicle Fleet.
- **CRUD Rules**: Vehicles (and their count, capacity, `transitSpeedKmh`, and `loadUnloadTimePerPersonSeconds`) can be freely added, modified, or removed while the twin is paused.
- **Realistic Map-Distance Kinematics & True 1:1 Twin Clock**:
  - Every route polyline (`approachCoords` and `evacCoords`) has its exact vertex-to-vertex geodesic segment lengths computed in meters via the spherical Haversine formula (`haversineMeters` / `buildCumulativeDistances`) over the underlying OpenStreetMap coordinates.
  - The twin clock runs at a true 1:1 ratio with wall-clock time at `1x` playback speed (`deltaTwinSec = wallDeltaSec * twinSpeed`), and each vehicle advances along its route polyline by $\Delta d = v_{\text{m/s}} \cdot \Delta t_{\text{twin}}$ where $v_{\text{m/s}} = \text{transitSpeedKmh} \times \frac{1000}{3600}$. For example, a vehicle configured at `25 km/h` (`6.944 m/s`) traversing a `3.0 km` OpenStreetMap route takes exactly `432` twin seconds (`07:12`).
- **Initial Depot Dispatch via Closest Evacuation Route vs. Subsequent Empty Return Routing**:
  - **Initial Dispatch from Designated Fleet Parking Stations via Closest Evacuation Route ($t = 0$ and Newly Added Fleets)**: Each evacuation route is paired by spatial proximity (`assignFleetsToRoutesByProximity` / `findClosestEvacuationRoute`) with its closest Vehicle Fleet parking station (`fleet.location`). When buses depart from their parking station (`fleet.location`), they travel along an obstacle-avoiding street connector (`computeApproachViaClosestPointOnRoute`) to the **closest point on their closest evacuation route** (`findClosestPointOnPolyline(fleet.location, route.coordinates)`) and then **follow that evacuation route polyline from there (`buildRouteSuffixToPickup`) all the way to the Pickup Location (`route.pickupLocation`)**.
  - **Subsequent Empty Return Trips (Post-Offload)**: After completing passenger unloading at a Target Area shelter, empty vehicles return to pick up additional population by reversing the existing computed evacuation route polyline (`Target Area -> Pickup Location`) at `transitSpeedKmh`.
- **Progressive Passenger Loading at Pickup Locations & Dual Departure Rule (80% Occupancy OR 10 Minutes Waiting Time)**:
  - When a vehicle arrives at a Source Area Pickup Location (Blue Square), a waiting timer (`waitingAtPickupSeconds`) starts at `00:00` and waiting evacuees board the vehicle at a rate governed by `loadUnloadTimePerPersonSeconds` (`1` person per `loadUnloadTimePerPersonSeconds` seconds per active vehicle in the convoy, with fractional progress accumulated across ticks via `loadingProgressRemainder`).
  - Lead waiting vehicles at a Pickup Location reserve their required queue seats up to 80% capacity so they fill and depart first without splitting non-overflow queues across waiting vehicles.
  - The vehicle waits and boards at the Pickup Location until **whichever of the following events happens first**:
    1. **80% Occupancy Reached**: `currentOccupancy >= 0.80 * maxCapacity`.
    2. **10 Minutes Waiting Time Elapsed**: `waitingAtPickupSeconds >= 600` (10 minutes of twin time).
    3. **Final Evacuees Boarded**: All remaining evacuees for that pickup/source area have finished boarding.
  - Provided there is **at least 1 passenger** onboard (`currentOccupancy >= 1`), the vehicle immediately departs along the computed route to the Target Area shelter.
- **Progressive Passenger Unloading at Target Shelters (`status: 'unloading'`)**:
  - When a loaded vehicle reaches its Target Area shelter, it enters `status: 'unloading'` and unloads passengers into the shelter at a rate governed by `loadUnloadTimePerPersonSeconds` (`1` person per `loadUnloadTimePerPersonSeconds` seconds per active vehicle in the convoy, with fractional progress accumulated via `unloadingProgressRemainder`).
  - As passengers step off the vehicle on each tick, they are transferred from `veh.currentOccupancy` (in-transit) to `target.currentOccupancy` (`totalEvacuated`), preserving exact population conservation ($\text{totalEvacuated} + \text{totalInTransit} + \text{totalRemainingAtSource} = \text{Total Population}$) at every tick. Once `currentOccupancy` reaches `0`, the vehicle departs empty along the reversed route polyline to pick up more people (or marks itself `'completed'` if the source zone is cleared).

### 3.5 Brussels Metro Network & Underground Train Evacuation
Underground rapid-transit rail network for the Region of Brussels, backed by GeoParquet datasets [`data/brussels_metro_lines.parquet`](data/brussels_metro_lines.parquet) (8 directional STIB Metro track geometries across Lines `1`, `2`, `5`, and `6`) and [`data/brussels_metro_stations.parquet`](data/brussels_metro_stations.parquet) (60 STIB Metro stations with `name_fr`, `name_nl`, `stop_id`, `line`, and point geometry):
- **Server & Static Data Pipeline**:
  - Server-side Python script [`server/brussels_metro.py`](server/brussels_metro.py) (exposed at `GET /api/brussels-metro/network` in [`vite.config.ts`](vite.config.ts)) reads both Parquet files via `geopandas`, reprojects geometries to `EPSG:4326` (`[lat, lng]`), and returns all line segments and stations, with pre-parsed fallback data in [`src/data/brusselsMetroData.ts`](src/data/brusselsMetroData.ts).
- **Brussels Region Geospatial Activation Check (`hasAnyAreaInBrussels`)**:
  - Evaluated via `BRUSSELS_REGION_BOUNDS` (`lat: 50.76..50.95`, `lng: 4.22..4.52`) in [`src/services/brusselsMetroService.ts`](src/services/brusselsMetroService.ts). The **`Brussels Metro`** UI section (`#brussels-metro-section`) is rendered **if and only if** at least one Source Area or Target Area polygon lies within the Region of Brussels.
- **Station-in-Area Detection (`findBrusselsMetroStationsInAreas`)**:
  - Automatically checks all 60 STIB Metro stations against every Source Area and Target Area polygon using `turf.booleanPointInPolygon`.
  - Lists all matched stations inside Source Areas (`#brussels-metro-source-stations`) and inside Target Areas (`#brussels-metro-target-stations`) with their station name, parent area name, and served metro line badges (`M1` `#B5378C`, `M2` `#ED6C23`, `M5` `#F6A90B`, `M6` `#0066A3`).
- **Static Underground Metro Corridors, Station Pickup/Drop-Off Establishment & Train Evacuation (`buildBrusselsMetroEvacuationCorridors` & `appendMetroPickupsAndTrains`)**:
  - When at least one metro station lies inside a Source Area and at least one metro station lies inside an active (non-disabled) Target Area, an evacuation control panel (`#brussels-metro-evacuation-controls`) appears with:
    1. Checkbox **`Use these stations for evacuation`** (`#chk-use-metro-for-evacuation`, `useForEvacuation: boolean`, enabled by default).
    2. Input **`number of trains available`** (`#input-metro-trains-available`, default `8` trains).
    3. Input **`capacity of each train`** (`#input-metro-train-capacity`, default `300` passengers/train).
  - **Source Area Metro Stations as Pickup Points & Target Area Metro Stations as Drop-Off Points**:
    - Every metro station located inside a Source Area is established as a **Metro Pickup Point** (`location: corridor.sourceStation.position`), and every metro station located inside an active Target Area is established as a **Metro Drop-Off Point** (`dropOffLocation: corridor.targetStation.position`, `metroTargetStationName: corridor.targetStation.name_fr`).
    - `buildBrusselsMetroEvacuationCorridors` connects every Source Area metro station to its optimal active Target Area metro station (and ensures every active Target Area metro station is connected from its optimal Source Area metro station) along the **exact static STIB metro rail geometry** (`computeMetroTrajectoryBetweenStations`, preferring direct same-line connections first and supporting cross-line transfers at STIB interchange hubs such as `Gare de l'Ouest`, `Beekkant`, and `Arts-Loi`).
  - **Independence from Street Route Computation & Immunity to Avoid Areas**:
    - Metro lines are fixed underground rail trajectories (`isMetro: true`). Clicking **`Compute Evacuation Routes`** is not required when evacuating via Brussels Metro (users can run Metro-only scenarios without any street routes or street vehicle fleets), and surface **`Avoid Areas`** do **not** block or detour underground metro trains.
    - For any Source Area served by active Brussels Metro corridors, all population clusters inside that Source Area (`compliant`, `disoriented` 2D Brownian walk, and `self-directed`) converge directly to the Source Area's interior **Metro Station Pickup Point(s)** so the station platforms and Metro trains are exclusively and effectively used to evacuate that Source Area.
  - **Underground Train Twin & Platform Dispatch Cadence (`appendMetroPickupsAndTrains` & `stepTwinState`)**:
    - Each available train (`1..trainCount`, distributed across active corridors) is instantiated as an individual `ActiveVehicleUnit` (`vehicleType: 'Metro'`, `unitCount: 1`, `maxCapacity: trainCapacity`, transit speed `45 km/h`, multi-door boarding/alighting `0.2 s/person`) starting at its Source Area Metro Station Pickup Point (`corridor.sourceStation.position`) with short staggered platform headways (`tIdx * 18s`).
    - While waiting at a Source Area Metro Station Pickup Point, a Metro train boards waiting evacuees at `0.2 s/person` (pooling across sibling corridors sharing the same Source Station platform when needed) and departs along the exact metro line polyline (`status: 'to_target'`) as soon as it reaches **80% occupancy**, **OR** all remaining evacuees have boarded, **OR** the platform queue is emptied (`remainingQueueForVeh === 0`) after at least `25s` of platform dwell time (`reachedMetroCadence`) with at least `1` passenger onboard.
    - Upon reaching the **Target Area Metro Station Drop-Off Point** (`corridor.targetStation.position`), the train transitions to `status: 'unloading'` (`0.2 s/person`) to disembark passengers into the Target Area shelter occupancy, and then returns empty (`status: 'to_pickup'`) along the reversed metro line polyline back to the Source Area Metro Station Pickup Point for subsequent trips until 100% of the Source Area is evacuated.

## 4. Operational Rules for Mid-Twin Pause, Editing & Restart

### 4.1 Modification Constraints
1. **Pause Requirement**: No area (Source, Target, Avoid) or vehicle definition can be added, modified, disabled, or removed unless the twin is **paused** (`isTwinning === false`). While the twin is running, all entity modification controls are locked.
2. **Area Removal with Confirmation Popup**: Every Source Area, Target Area, and Avoid Area has a **`Remove`** button in the Parameters panel. Clicking **`Remove`** displays a confirmation popup window (`#confirm-remove-area-modal`) asking the user to confirm; if confirmed, the area is removed from the configuration, map, routes, and twin memory.
3. **Source, Target & Avoid Area Disabling**: Every Source Area, Target Area, and Avoid Area includes a **`Disable` / `Enable`** button (`disabled: boolean`), allowing operators to temporarily disable an area while the twin is paused.
4. **Avoid Areas & Vehicles**: Avoid Areas and Vehicle Fleets can be added or removed whenever the twin is paused.

### 4.2 Twin Restart, Mid-Pause Route Recalculation & Off-Route Bus Re-Routing Mechanics
When the simulation is stopped (`isTwinning === false`), areas change, and routes are recalculated (either by clicking **`Compute evacuation routes`** while paused or automatically when clicking **`Run twin`**):
1. **Dynamic Route Recomputation**:
   - The routing engine recomputes obstacle-avoiding evacuation routes to evacuate all remaining and newly added people in active Source Areas into active Target Areas (avoiding active Avoid Areas).
2. **On-Route vs. Off-Route Bus Reconciliation (`reconcileTwinOnRestart` & `computeRejoinPathToClosestRoute`)**:
   - **Buses Still on Their Assigned Evacuation Route**: Any bus whose current position remains within `40 meters` of its originally assigned evacuation route polyline (`findClosestPointOnPolyline(veh.currentPosition, origRoute.coordinates).distanceMeters <= 40`) continues along that evacuation route from its current position (`buildRouteSuffixToTarget` if `currentOccupancy > 0`, or `buildRouteSuffixToPickup` if `currentOccupancy === 0`).
   - **Buses Off Any Evacuation Route After Reconfiguration**: Any bus that was on an evacuation route before reconfiguration and is now off its assigned evacuation route (`distanceMeters > 40` or its original route was removed/reconfigured) **directs itself to the closest active evacuation route** (`findClosestEvacuationRoute(veh.currentPosition, activeStreetRoutes)` / `computeRejoinPathToClosestRoute`), traveling from its current position via an obstacle-avoiding street path to the closest point on that closest evacuation route and then following that evacuation route from there (toward the Pickup Location if `currentOccupancy === 0`, or toward the Target Area shelter if `currentOccupancy > 0`), rather than continuing along the old route it had originally been assigned.

## 5. UI Layout & UX Architecture

The viewport is divided into a **4-Panel Cockpit Layout** (`100vw × 100vh`, non-scrolling outer flex container) where the **Left Control Panel**, **Bottom Log Panel**, and **Right Telemetry Panel** are **independently collapsible**, dynamically giving all reclaimed horizontal and vertical space to the **Center Map Viewport**:

```
+-------------------+-----------------------------------+-------------------+
|                   |                                   |                   |
|                   |                                   |                   |
|                   |            CENTER MAP             |                   |
|    LEFT PANEL     |         (OSM + Overlays)          |    RIGHT PANEL    |
|   (Parameters &   |   Default: 50% W × 75% H          |  (Live Telemetry  |
|     Controls)     |   Expands dynamically (`flex: 1`) |   & Analytics)    |
|                   |   up to ~100% W × ~100% H         |                   |
|  25% W (or 38px   +-----------------------------------+  25% W (or 38px   |
|  collapsed rail)  |           BOTTOM PANEL            |  collapsed rail)  |
|   100% Height     |      (System & Twin Logs)         |   100% Height     |
|   [Collapsible]   |   25% H (or 36px collapsed bar)   |   [Collapsible]   |
+-------------------+-----------------------------------+-------------------+
```

- **Independent Panel Collapse & Dynamic Center Map Expansion**:
  - **Left Panel Collapse (`#btn-toggle-left-panel`)**: Collapses the Left Control Panel (`25%` width) into a `38px` vertical tactical rail displaying an expand button and rotated `EVAC-TWIN — PARAMETERS & CONTROLS` label.
  - **Right Panel Collapse (`#btn-toggle-right-panel`)**: Collapses the Right Situational Telemetry Panel (`25%` width) into a `38px` vertical tactical rail displaying an expand button, a live evacuation progress percentage badge (`{progressPercent}%`), and rotated `SITUATIONAL TELEMETRY` label.
  - **Bottom Log Panel Collapse (`#btn-toggle-bottom-panel`)**: Collapses the Bottom Log Console (`25vh` height) into a compact `36px` header bar that retains the event counter badge, a live one-line preview of the most recent log entry, and an `Expand Logs` button.
  - **Automatic Map & Heatmap Canvas Resize (`ResizeObserver`)**: The Center Column (`.cockpit-center-column`) and Map Area (`.cockpit-map-area`) use `flex: 1; min-width: 0; min-height: 0;` and attach a `ResizeObserver` to the Leaflet container in [`EvacuationMap.tsx`](src/components/EvacuationMap.tsx) that automatically calls `map.invalidateSize({ animate: false })` and `renderHeatmapCanvas()` whenever any panel is collapsed or expanded.

### 5.1 Left Panel: Parameters & Controls (`25% Width × 100% Height`, Independently Collapsible)

## 7. Preset Scenarios (`data/scenarios/*.pkl`)

All available preset scenarios are loaded **strictly dynamically** when the application starts from `.pkl` files in the [`data/scenarios/`](data/scenarios) directory via [`server/scenarios.py`](server/scenarios.py) (served at `/api/scenarios` by [`vite.config.ts`](vite.config.ts)). Scenario contents (polygons, coordinates, Source/Target/Avoid areas, vehicle fleets, names, etc.) are **never hardcoded** within the application source code ([`src/data/presets.ts`](src/data/presets.ts) defines only the `PresetScenarioData` TypeScript interface) or any other configuration files.

### 7.1 `.pkl` Scenario File Schema
Each `.pkl` file in `data/scenarios/` is a pickled Python `dict` containing:
- `name`: `str` — Human-readable scenario name displayed in the Preset Scenario selector.
- `source_areas`: `list[dict]` — Each dict has `name` (`str`), `population` (`int`), `population-distribution` (`{'compliant': int, 'self-directed': int, 'disoriented': int}`), and `shape` (Shapely `Polygon`, `MultiPolygon`, `LineString`, or `MultiLineString` in `(lon, lat)` WGS84).
- `target_areas`: `list[dict]` — Each dict has `name` (`str`), `capacity` (`int`), and `shape` (Shapely geometry in `(lon, lat)` WGS84).
- `avoid_areas`: `list[dict]` — Each dict has `name` (`str`) and `shape` (Shapely geometry in `(lon, lat)` WGS84).
- `vehicle_fleets`: `list[dict]` — Each dict has `name` (`str`), `count` (`int`), `capacity_per_unit` (`int`), `load_unload_secs_per_person` (`float`), `speed` (`float`, in `km/h`), `lat` (`float`), and `lon` (`float`).

### 7.2 Dynamic Startup Discovery & Initialization Flow
1. On application mount, [`src/App.tsx`](src/App.tsx) calls `GET /api/scenarios`, which executes [`server/scenarios.py`](server/scenarios.py) to scan `data/scenarios/*.pkl` at runtime, deserialize the Shapely geometries and scenario attributes, compute the viewport `center` and `zoom` from the scenario's bounding box, and return the discovered list of `PresetScenarioData` objects.
2. [`src/App.tsx`](src/App.tsx) populates the Preset Scenario selector with the dynamically discovered scenarios, automatically activates the first scenario, distributes the evacuee clusters spatially uniformly inside each Source Area (`initializeTwinState`), and computes the initial street evacuation routes (`computeAllEvacuationRoutes`).
3. Adding, modifying, or removing any `.pkl` file in [`data/scenarios/`](data/scenarios) automatically updates the available scenarios on next load/startup without any code or configuration changes.
